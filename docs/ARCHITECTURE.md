# Архитектура TRON Flow Tracker

## Коротко

Один Mac, три процесса, одна база:

```
                         ┌──────────────────────────── Mac (launchd) ───────────────────────────┐
                         │                                                                      │
 Браузер ──HTTPS/LAN──►  │  web (Next.js 16)                    worker (Node, tsx)              │
 (админ, пароль)         │  ├─ proxy.ts: проверка сессии        ├─ очередь Job (SYNC/EXPAND/…)  │
                         │  ├─ страницы: дашборд, кошельки,     ├─ бэкфилл истории новых адресов│
                         │  │   карточка, граф (Cytoscape.js)   ├─ firehose: ивенты USDT ──┐    │
                         │  └─ /api/*: CRUD, граф, CSV, jobs    ├─ балансы (balanceOf)     │    │
                         │        │  ставит задачи ▲            └─ heartbeat / лимиты      │    │
                         │        ▼                │                    │                  │    │
                         │  ┌──────────────── PostgreSQL 17 ───────────────┐              │    │
                         │  │ Wallet · Label · Transfer · BalanceSnapshot │              │    │
                         │  │ Job · SyncState                              │              │    │
                         │  └──────────────────────────────────────────────┘              │    │
                         │  backup (04:00): pg_dump → ~/tronflow-backups                   │    │
                         └─────────────────────────────────────────────────────────────────┼────┘
                                                                                           ▼
                                                                          TronGrid API (api.trongrid.io)
```

Ключевое правило: **в TronGrid ходит только воркер**. Веб ставит задачи в таблицу `Job`
и опрашивает их статус. Так один rate limiter, один учёт суточного лимита, и медленные
запросы к блокчейну не держат HTTP-запросы веба.

## Получение данных

| Задача | Эндпоинт TronGrid | Когда | Стоимость |
|---|---|---|---|
| История нового кошелька | `GET /v1/accounts/{a}/transactions/trc20` (desc) | один раз при добавлении | ≤ `BACKFILL_MAX_PAGES` запросов (100 = 20k переводов) |
| Новые переводы (firehose) | `GET /v1/contracts/{USDT}/events?event_name=Transfer` (asc) | каждые 15 с | ~12k запросов/сутки — **не зависит от числа кошельков** |
| Новые переводы (poll) | `GET /v1/accounts/{a}/transactions/trc20` (asc от курсора) | раз в `POLL_INTERVAL_SEC` на кошелёк | N кошельков × 720/сутки |
| Баланс | `POST /wallet/triggerconstantcontract` `balanceOf(address)` + `/wallet/getaccount` | после новых переводов + раз в 6 ч | 2 запроса на кошелёк |
| Раскрыть узел графа | `GET /v1/accounts/{a}/transactions/trc20` (desc) | по кнопке | ≤ 5 запросов |

Почему firehose по умолчанию: USDT на TRON — ~2–3 млн переводов в сутки (~30/с), это ~150
страниц по 200 ивентов в час. Для 200 кошельков poll раз в 2 минуты стоил бы 144k запросов/сутки —
больше бесплатного лимита (100k). Firehose читает весь поток одним курсором и фильтрует по адресной книге.

Надёжность:
- **Идемпотентность**: уникальный ключ `(txHash, from, to, amount)`; окна запросов перекрываются, дубликаты отбрасываются.
- **Курсоры**: firehose-курсор в `SyncState`, per-account — `Wallet.syncCursor`; двигаются постранично, прерванная работа продолжается.
- **Простой Mac'а**: если firehose отстал > 2 ч, воркер догоняет каждый кошелёк per-account от его курсора, а не листает миллионы чужих ивентов.
- **Только подтверждённые блоки** (`only_confirmed=true`), задержка ~1 мин.
- **Защита от спама**: нулевые переводы (address poisoning) не сохраняются.
- **Лимит**: запросы считаются в `SyncState`; при достижении `TRONGRID_DAILY_BUDGET` второстепенные задачи (бэкфилл, раскрытие) ставятся на паузу, живой поток и балансы продолжают работать.
- **Один воркер**: `pg_try_advisory_lock` — вторая копия ждёт.

## Модель данных (`prisma/schema.prisma`)

| Таблица | Назначение |
|---|---|
| `Wallet` | Адресная книга: `address`, `label`, `category` (EXCHANGE/OTC/TRADER/WHALE/SUSPICIOUS/UNKNOWN), `notes`, `isWatched` (false — раскрытый контрагент), балансы, курсоры синхронизации, `historyFrom` |
| `Label` + `WalletLabel` | Теги, многие-ко-многим; `source` = MANUAL или AUTO (проставлен эвристикой графа) |
| `Transfer` | Каждый Transfer-ивент USDT: `txHash`, `blockTimestamp` (timestamptz), `fromAddress`, `toAddress`, `amount NUMERIC(38,6)`. Адреса — строки, не FK: контрагентов тысячи. Индексы `(from, ts)`, `(to, ts)`, `(ts)` |
| `BalanceSnapshot` | История баланса для графика |
| `Job` | Очередь задач веб → воркер |
| `SyncState` | Курсор firehose, heartbeat воркера, счётчик запросов за день |

Почему PostgreSQL, а не Neo4j: связи 1–3 шага считаются SQL-запросом по индексам from/to и
графом в браузере; отдельная графовая БД нужна при десятках миллионов рёбер и глубоких обходах
на сервере — это этап 3 дорожной карты.

## Аналитика (`src/lib/analytics.ts`)

Всё считает Postgres:
- **Оборот** — сумма переводов, касающихся книги; перевод между двумя кошельками книги считается один раз (`internal`), а не как приток + отток.
- **Средний и медианный** размер перевода (медиана устойчива к единичным крупным переводам).
- **Уникальные контрагенты** — вне адресной книги.
- **Пиковые часы / дни** — в часовом поясе `ANALYTICS_TZ` (Asia/Yerevan).

## Граф и эвристики (`src/lib/graph/`)

Чистые функции, работают в браузере, покрыты тестами:
1. Переводы агрегируются в рёбра `from→to` (сумма, количество, первый/последний).
2. Фильтры: мин. сумма (до агрегации), даты, глубина от стартовых узлов (BFS без учёта направления), лимит рёбер.
3. Эвристики:
   - **collector / distributor (хабы)** — ≥ 8 разных отправителей / получателей;
   - **splitter** — 1–2 источника → ≥ 5 получателей, ≥ 80 % входа ушло дальше;
   - **transit** — вход ≈ выход (±10 %), оборот ≥ 1000, баланс ≤ 10 % оборота;
   - **apex** — ≥ 3 соседа-коллектора (или раздатчика): двухуровневая пирамида;
   - **cycle** — простые направленные циклы длиной 3–5 (A↔B исключены как шум «депозит/вывод»).

Пороги — `DEFAULT_PATTERN_CONFIG` в `patterns.ts`. Это подсказки аналитику, не вердикт.

Визуализация — **Cytoscape.js** + fCoSE: canvas-рендер тысяч узлов, направленные рёбра с
подписями, стили по селекторам, иерархическая раскладка для пирамид. Цвет узла = категория,
форма узла = категория (дублирует цвет), обводка + текстовый бейдж = паттерн.

## Ликвидность и давление на курс (`src/lib/liquidity.ts`)

«Рынок» — кошельки категорий «Обменник» и OTC (если их нет — вся книга). Для окон 1, 4 и 24 ч:

| Метрика | Формула | Смысл |
|---|---|---|
| Приток | Σ переводов извне на кошельки рынка | клиенты сдают USDT → давление продаж |
| Отток | Σ переводов с кошельков рынка наружу | клиенты покупают USDT → давление покупок |
| Нетто | приток − отток | |
| Дисбаланс | (приток − отток) / (приток + отток), от −1 до +1 | стрелка прибора давления |
| Интенсивность | оборот окна / средний оборот такого же окна за прошлые 7 дней | ниже ×0,3 — сигнал слабый |
| Скорость обращения | весь оборот рынка за 24 ч / суммарный баланс рынка | как быстро оборачиваются деньги |

Переводы между кошельками рынка — внутренние: в давлении не участвуют, в скорость обращения входят.
Пороги прибора: |дисбаланс| < 0,15 — баланс, до 0,3 — слабое, до 0,5 — умеренное, дальше — сильное давление.

## Паттерны (`src/lib/patterns/`)

Поведенческие детекторы по сырым переводам (с учётом времени и сумм), дополняют структурные роли графа:

- **Рассылка (FAN_OUT)** — скользящее окно 60 мин: максимум разных получателей у отправителя; ≥ 10 получателей;
  уверенность растёт с числом получателей и схожестью сумм (коэффициент вариации ≤ 35 %).
- **Сбор (FAN_IN)** — ≥ 20 отправителей и ≥ 30 переводов, медиана ≤ 1 000 USDT; плюс к уверенности, если собранное
  уходит дальше редкими крупными переводами.
- **Кольцо (LOOP)** — граф урезается до ядра (у каждого узла есть вход и выход), в нём ищутся циклы длиной 3–5,
  затем для цикла подбирается цепочка реальных переводов: по времени по порядку, за ≤ 72 ч, на каждом шаге дальше
  уходит 50–105 % суммы. Структурные «циклы», которые не складываются по времени или теряют сумму, отбрасываются.

Воркер сканирует 7 дней раз в час (`PATTERN_SCAN_MIN`), находки хранятся в `PatternFinding` с устойчивым ключом:
повторный скан обновляет находку, отклонённые не возвращаются. «Поставить метку» добавляет AUTO-метку
(рассылка / сбор / кольцо) всем адресам находки. Пороги — `DEFAULT_DETECT_CONFIG` в `detect.ts`.

## Уведомления в Telegram (`src/lib/alerts/`, `src/lib/telegram.ts`)

Движок работает в воркере после каждого цикла загрузки:

| Правило | Условие | Защита от шума |
|---|---|---|
| Крупный перевод | один перевод ≥ порога по кошелькам области | только «живые» переводы (не старше 20 мин), история и бэкфилл не уведомляют |
| Всплеск объёма | объём за N мин ≥ норма × (1 + X %) и ≥ минимума | норма по реально покрытому данными времени (нужно ≥ 1 сут истории); не чаще `cooldownMin` |
| Новый адрес | контрагент не встречался ни в одном более раннем переводе и не записан в книгу | только для кошельков с загруженной историей |
| Новый паттерн | новая находка скана нужного типа с уверенностью ≥ порога | |

Каждое событие пишется в `AlertEvent` с уникальным ключом — повторов не бывает даже после перезапуска.
Больше 5 событий одного правила за цикл уходят одной сводкой. Отправка — Bot API напрямую (`fetch`), пауза
1,1 с между сообщениями, повтор после `429 retry_after`. Без токена события сохраняются в журнал со статусом
«только журнал». Токен — в `.env`, чат выбирается в интерфейсе (кнопка «Найти чаты» читает `getUpdates`).

## Безопасность

- Один администратор: пароль в `.env`, сессия — HMAC-подписанная httpOnly cookie (SameSite=Strict), 7 дней.
- Проверка сессии и в `proxy.ts`, и в каждом API-роуте / layout.
- Перебор пароля: 5 ошибок за 15 минут на IP → блокировка.
- По умолчанию слушает только `127.0.0.1`; доступ из локальной сети — `HOST=0.0.0.0`.
- `.env` создаётся с правами 600.
- CSV экранируется от формул Excel.

## Дорожная карта

**Этап 1 — MVP (готово):** адресная книга с импортом, бэкфилл, firehose, балансы, дашборд
(оборот, средний/медиана, контрагенты, пиковые часы/дни), карточка кошелька, граф с
фильтрами и эвристиками, раскрытие узлов, CSV, авторизация, launchd, бэкапы, тесты.

**Этап 1.5 (готово):** уведомления в Telegram (крупный перевод, всплеск объёма, новый адрес, паттерн),
детекторы рассылки/сбора/колец с разметкой, прибор давления на курс и страница ликвидности.

**Этап 2 — эксплуатация:**
- Уведомление «воркер молчит» с внешнего наблюдателя (сам воркер о своём падении сообщить не может).
- Пороги детекторов в интерфейсе; сохранённые «расследования» (набор узлов + фильтры).
- Курс USDT/AMD (спреды) из внешнего источника рядом с оборотом.
- Материализованные дневные агрегаты при > 10 млн переводов.

**Этап 3 — масштаб:**
- Собственная TRON-нода с event-плагином (Kafka) вместо TronGrid — без лимитов и задержек.
- Партиционирование `Transfer` по месяцам; Neo4j/Apache AGE для глубоких обходов на сервере.
- Несколько пользователей с ролями.
